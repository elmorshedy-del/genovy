Architecture

One backbone, three operating layers.

The website is only the surface. Underneath it, Genovy maintains a normalized knowledge layer, a patient-specific case layer, and a product layer that turns both into summaries, guidance, and future clinic workflows.

Knowledge layer

Canonical rare-disease network

Diseases, phenotypes, genes, variants, trials, and evidence sources are mapped into a shared graph.

  • Canonical IDs and aliases
  • Evidence-backed relationships
  • Versioned sync history per source

Case layer

Structured patient workup

Uploaded reports become a timeline of symptoms, tests, findings, and unresolved questions.

  • Timeline stitching across many documents
  • Normalized phenotype and workup extraction
  • Traceability back to source files

Product layer

Readable outputs for real decisions

The graph turns into doctor briefs, next-step guidance, trial matching, and future clinic workflows.

  • Doctor-ready summaries
  • Workup and referral guidance
  • Future eligibility and trial modules

Schema

The graph stores entities, relationships, and evidence separately.

Rare-disease logic breaks if you flatten everything into a spreadsheet. Genovy keeps canonical entities, the links between them, and the source evidence for those links in separate layers so the reasoning stays inspectable.

Entity families

Nodes in the network

Disease

Canonical disease families and specific conditions anchored to ontology IDs.

Phenotype

Symptoms, findings, and clinically meaningful negatives mapped to HPO-style concepts.

Gene

Gene-level associations stay separate from disease and variant-level evidence.

Variant

Variant-specific evidence can diverge from the broader gene signal and must stay first-class.

Trial

ClinicalTrials condition and recruitment links connect cases to research opportunities.

Source record

Original upstream payloads remain preserved for provenance, reprocessing, and audits.

Relationship model

Edges carry context, not just links

disease → has phenotype gene → associated with disease gene → associated with phenotype variant → pathogenic for disease trial → recruits for disease case → has phenotype case → lacks phenotype case → has finding

Evidence first

Every relationship can point back to a source, record key, sync run, and evidence type.

Many-to-many by default

One gene can connect to many diseases, and overlapping phenotypes can remain unresolved until more evidence arrives.

Versioned freshness

Source state records the last successful sync, version string, and summary so the graph can be refreshed safely.

Pipeline

How the backbone fills itself.

Source syncs are designed as refreshable stages, not one-off imports. Each run records version, summary, and provenance so the network can stay current and auditable.

01

Fetch source payloads

Pull ontology releases and public APIs from MONDO, HPO, ClinVar, and ClinicalTrials.gov.

02

Normalize canonical objects

Upsert entities, aliases, and cross-references so multiple identifiers resolve to one concept.

03

Write evidence-backed edges

Persist graph relationships separately from the evidence that justifies each link.

04

Track sync freshness

Store last successful run, version, and source-level summaries so stale connectors are visible.

05

Power case workflows

Feed the future patient case layer, specialist summaries, and next-step workup guidance.
